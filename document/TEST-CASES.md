## 一、执行前必须准备的东西（重点）

下面这些缺一项，对应用例就跑不通。**标「阻塞」的没有就无法开始。**

| # | 资源 | 用途 | 是否阻塞 | 说明 |
|---|---|---|---|---|
| 1 | **1 个微信小程序 AppID + 上传密钥 `.key` 文件** | 构建上传、体验版二维码 | **阻塞** | 一个够用。并发用例改为同 AppID 内验证 robot 分配，见 G13 |
| 2 | 代码上传 IP 白名单（**未开启则不用管**） | `miniprogram-ci` 上传前置条件 | 否 | 未开启 = 微信不限制来源 IP，可直接跑；已开启 = 必须把本机出口 IP 加进去，否则报 `-10008 invalid ip` |
| 3 | **一个原生小程序仓库**（clone 下来即可上传，无需 build） | 构建成功路径 | **阻塞** | 需确认源码位置与是否用 npm 包，见下方「原生项目两项前置」 |
| 4 | 公开 Git 仓库地址（任意公开仓库） | 匿名克隆用例 | 否 | 例如 `https://github.com/octocat/Hello-World.git` |
| 5 | 私有 Git 仓库 + HTTPS PAT | 凭证用例 | 否 | 缺了只能测匿名克隆 |
| 6 | 私有 Git 仓库 + SSH 私钥 | SSH 凭证用例 | 否 | 缺了跳过 C2 / C5-SSH |
| 7 | **一个企业微信群机器人 / 钉钉 / 飞书 webhook URL** | 通知用例 | 否 | 缺了构建仍能跑，只是通知断言跳过 |
| 8 | 测试账号 × 4 | 权限用例 | **阻塞** | 见下表 |
| 9 | 能访问微信后台的权限 | 人工核对「开发版本」列表 | 否 | robot 编号在后台不可见，只能用数据库 `robot_id` 断言；后台只用来确认上传真的进去了 |

### IP 白名单到底要不要开

**结论：不用提前开，先跑。** 实际判定只有三种情况：

| 状态 | 结果 |
|---|---|
| **未开启**（默认） | 微信不限制来源 IP → 上传正常 ✅ |
| 已开启 + IP 在列表 | 正常 ✅ |
| 已开启 + IP 不在列表 | `errCode -10008, invalid ip` ❌ |

只有第三种会失败。所以流程是：**直接跑一次构建，报 `-10008` 了再去开白名单加 IP，没报就不用管。**

> 微信官方文档里那句「未配置 IP 白名单的将无法使用 miniprogram-ci」容易误读，
> 它实际指的是「开启了白名单但没配 IP」。同一页面又写着「可选择不对 IP 进行限制」。

**但安全上要清楚代价**：未开启 = 任何拿到 `.key` 的人，从任何 IP 都能往你的小程序上传代码。
微信官方原文是「建议所有开发者默认开启这个选项，降低风险」。测试阶段不开没关系，
**正式给别人用之前建议开**。

### 原生项目两项前置（容易踩，先确认）

原生小程序没有 build 步骤，平台把 **`distPath` 为空 → 直接用仓库根目录** 当小程序目录，把 **`distPath` 有值 → 用该子目录**。所以：

| 项 | 填错会怎样 | 怎么确认 |
|---|---|---|
| **源码位置** | 源码在 `miniprogram/` 子目录却留空了「产物目录」→ 把仓库根当小程序根，上传出一个空包 / `app.json` 找不到 | 仓库根下有 `app.json` 就是根目录，否则填子目录路径 |
| **是否用 npm 包** | 用了 npm 但 `miniprogram_npm` 是本地构建的、没进仓库 → 平台不会自动「构建 npm」，上传包缺依赖 | 见第四节 F-3 |

### 单 AppID 对用例的影响（重要，避免误判）

微信同一 AppID 只有一个**体验版**，任何一次上传都会覆盖它，这与平台实现无关。所以：

- ❌ 不测「两个项目各自保留独立体验版」—— 微信层就不支持，两个 AppID 也不成立（那是两个不同小程序）
- ✅ 测「并发构建时 robot 分配不冲突、都上传成功」—— 这才是 30 个 robot 池子真正解决的问题（G13）
- ✅ 测「池子连续分配不重复」—— 单 AppID 下仍能验证池子逻辑正确（G14）

## 二、黄金路径（ego-lite 主流程，先跑这一条）

一条链路串起所有模块，跑通说明系统主体可用。**本路径以原生小程序为准。**

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 打开 `/login`，输入 `admin` / `admin123`，点「登录工作空间」 | 跳转 `/dashboard`，右上角显示用户名 |
| 2 | 进入「管理 → 凭证管理」，新建 HTTPS 凭证（名称 `e2e-cred`，填 PAT；仓库公开则任填） | 列表出现该凭证，`secret` 不显示明文 |
| 3 | 点该凭证的「测试」按钮 | 提示连接成功 |
| 4 | 进入「管理 → 机器人」，新建企微机器人（填 webhook）；无 webhook 则跳过本步 | 列表出现，可点「测试」发送成功 |
| 5 | 进入「项目」→「新建项目」：填名称、AppID、仓库地址、选凭证；**框架选「原生小程序」，构建命令与产物目录都留空**；上传 `.key` 文件 | 创建成功，跳转项目列表，状态正常 |
| 6 | 进入项目详情 →「构建历史」→「触发构建」，分支 `main`，版本 `1.0.0` | 出现一条 `PENDING` 记录，随后变 `RUNNING` |
| 7 | 点「查看日志」 | 终端实时滚动，依次出现 `[1/4] 克隆` → `[2/4] 安装` → `[3/4] 构建` → `[4/4] 上传`；**原生无 `package.json` 时第 2 步应显示「未找到 package.json，跳过依赖安装」，这是正常现象** |
| 8 | 等待构建结束 | 状态 `SUCCESS`，出现「下载」入口，二维码可预览，包体积列有数值（原生项目应为 MB 级，不是几 KB） |
| 9 | 打开「下载」抽屉，查看二维码 | 二维码图片正常显示（带签名 URL） |
| 10 | 回到列表，对该任务点「重试」 | 生成一条新的 `PENDING` 任务，版本号为新的时间戳 |
| 11 | 对第一条任务点「删除」 | 记录消失，磁盘日志与二维码同步清理 |
| 12 | 回到「仪表盘」 | 总项目数、今日构建、构建趋势、框架分布均与操作一致 |

**这条链路跑不通，后面的单点用例没有意义。**

> 第 8 步的「包体积」是单个最能说明问题的断言：**原生项目如果填错了产物路径，构建依然会 success，但包体积只有几 KB 甚至 0**。看到这种情况先查产物目录，不要怀疑上传链路。

### G. 构建

> 全部用例基于**原生小程序**。「原生无 build 步骤」是核心前提：没有 `package.json` 时
> 平台会跳过依赖安装，没有构建命令时跳过编译，这两步的「跳过」是正确行为，不是缺陷。

| ID | 场景 | 步骤 | 预期 | P |
|---|---|---|---|---|
| G1 | 手动触发（原生，源码在根目录） | 分支 main，版本 `1.0.0`，构建命令与产物目录均留空 | 建任务 → 入队 → 执行 → `success`；日志显示「未找到 package.json，跳过依赖安装」 | P0 |
| G2 | 版本号重复 | 用已成功的版本号再触发 | 409，提示更换版本号 | P0 |
| G3 | 非法分支名 | API 直接传 `main; ls` | 400「非法的分支名」，且不执行任何命令 | P0 |
| G4 | 构建成功产物完整 | 成功后查看任务详情 | `status=success`、`qrcodePath` 有值、`packageSize > 0`、`commitHash` 为 40 位 | P0 |
| G5 | 构建失败可诊断 | 用不存在的仓库地址触发 | `status=failed`，`failReason` 含错误原因；`logPath` 仍是纯路径 | P0 |
| G6 | 实时日志推送 | 构建中打开「查看日志」 | WebSocket 连续推送 `[1/4]…[4/4]`，无明显断流 | P0 |
| G7 | 历史日志回看 | 构建结束后再次打开日志 | 通过接口拉取完整日志，末尾显示「End of log」 | P0 |
| G8 | 取消 pending 任务 | 任务排队中立即取消 | 状态变 `canceled`，不产生微信上传 | P0 |
| G9 | 取消 running 任务 | 克隆阶段取消 | 状态 `canceled`，且**不会被后续流程覆盖成 success** | P0 |
| G10 | 重试构建 | 对失败任务点「重试」 | 新建任务，分支与项目一致，版本号为新时间戳 | P1 |
| G11 | 历史版本重传 | 对成功任务点「从历史版本重传」 | 新建任务，解压旧 ZIP 后直接上传，success | P1 |
| G12 | Webhook 触发 | 向 webhook 地址 POST GitHub 风格 payload | 建任务并执行，触发方式记为 Git Webhook | P1 |
| G13 | **并发构建的 robot 分配** | 同一项目快速连续触发两次（版本 `cc-1` / `cc-2`），间隔 < 1 秒 | 两条任务都 `success`；**数据库中 `robot_id` 不同**；微信侧无 robot 冲突报错 | P0 |
| G14 | 池子连续分配不重复 | 连续触发 5 个构建（版本 `pool-1..5`） | 5 条任务 `robot_id` 互不相同；worker 并发 3，其余排队不报错 | P2 |
| G15 | 机器人池耗尽 | 并发 30+ 任务 | 理论上是延迟重试、不消耗重试次数。**不要实跑**——会真的向微信发起 30+ 次上传，触发频率限制。改为代码审查 + G13/G14 覆盖 | P2 |
| G16 | 大仓库超时 | 用超大仓库触发 | 超时后任务置 failed，子进程被清理（无残留 node/git 进程） | P2 |
| G17 | 构建中断恢复 | 构建中 `kill -9` 后端进程后重启 | 僵死任务变 failed，机器人池恢复 30 个可用 | P1 |
| G18 | **原生包体积合理性** | 任一次成功构建后看「大小」列 | 原生小程序应为 **百 KB ~ 数 MB**；若显示几 KB 或 0，说明产物目录配错（把仓库根当小程序根），**先查路径不要怀疑上传** | P0 |
| G19 | 原生用 npm 包但未提交构建产物 | 若项目使用 `miniprogram_npm` 且未提交 → 构建可能 success 但运行时报错 | 这是已知限制 F-3，**视为预期行为**，不记为缺陷 | P2 |

**G13 的判定依据**（单 AppID 下唯一能验证的方式）：

```sql
SELECT id, version, robot_id, status
FROM build_tasks
WHERE project_id = '<项目ID>'
ORDER BY id DESC LIMIT 2;
```

两个 `robot_id` 必须不同。若相同，说明池子没生效（所有任务都拿了同一个号）。
若任务失败并提示 robot 相关错误，说明 `ci.upload` 的 `robot` 参数没传对。

> **不要再断言「体验版互不覆盖」**。微信同一 AppID 只有一个体验版，后上传的必然覆盖前面的，
> 这与是否用 robot 无关。robot 解决的是「并发上传互相顶掉导致失败」，不是「多个体验版共存」。

## 四、缺陷与修复记录

### F-1　项目级权限未启用 —— 已修复（2026-11-18）

**原问题**：`ProjectGuard` 采用「未声明角色即放行」，而 `RequireProjectRoles` 全项目零使用。结果是任何登录用户都能查看、修改、删除任意项目，能读别人的构建日志、取消别人的构建。

**修复内容**：

- project-core 的 6 个接口补上角色注解
- build-tasks 的 7 个接口补上角色注解
- `ProjectGuard` 支持 `:id` 与 `:taskId` 两种路由参数（原先只认 `projectId`，导致 `GET /projects/:id` 永远取不到项目 ID）

**当前权限矩阵**：

| 操作 | maintainer | developer | guest | 项目外 |
|---|---|---|---|---|
| 项目详情 / 构建历史 / 构建日志 | ✅ | ✅ | ✅ | 403 |
| 触发 / 取消 / 重试 / 重传 / 删除构建 | ✅ | ✅ | 403 | 403 |
| 改项目设置 / 管成员 / 删项目 | ✅ | 403 | 403 | 403 |
| 凭证 / 机器人 / 用户 / 审计 | 仅超管 | 仅超管 | 仅超管 | 仅超管 |

**已实测验证**（脚本跑通）：

```
项目外用户：详情 403 / 历史 403 / 触发 403
developer ：详情 200 / 历史 200 / 改设置 403 / 删项目 403 / 加成员 403 / 触发 201
```

单测覆盖见 `src/common/guards/project.guard.spec.ts`（8 条）。

> guest 目前**不能**触发构建。若产品上希望放开，调整 `BUILD_ROLES` 即可。

### F-2　守卫默认放行（设计问题，已通过补齐注解规避）

两个守卫都是「没配注解就放行」，漏配时不报错、只静默失去防护。本次给所有敏感接口补齐了注解，但设计本身仍是 fail-open。建议后续在启动时扫描控制器，校验「带了守卫的接口是否都声明了所需角色」，把漏配变成启动失败。

### F-3　原生小程序使用 npm 包时，平台不会「构建 npm」（已知限制，未修复）

**现象**：原生小程序如果引用了 npm 包，微信要求先把 `node_modules` 编译成
`miniprogram_npm`（开发者工具里的「工具 → 构建 npm」）。`miniprogram-ci` 支持在
上传时自动做这件事，但需要显式配置：

```ts
setting: {
  es6: true,
  minify: true,
  packNpmManually: true,
  packNpmRelationList: [{ packageJsonPath: './package.json', miniprogramNpmDistDir: './' }],
}
```

当前平台只传了 `es6` 和 `minify`，没有这两项。

**后果**：构建状态仍然 `success`、二维码照常生成，但包里 `miniprogram_npm` 是空的，
真机运行时会出现依赖找不到。**构建状态不会报错，这是最麻烦的地方。**

**本次测试怎么处理**：

- 若测试项目**不用 npm 包** → 不受影响，G1 直接通过
- 若用了 npm 包但 `miniprogram_npm` 已提交进仓库 → 不受影响
- 若用了 npm 包且依赖本地构建 → G19 记为「已知限制」，**不判为失败**

**修复方向**（待排期）：在 `miniprogram-uploader.service.ts` 的 `setting` 里补上
`packNpmManually` 与 `packNpmRelationList`，并在项目设置里暴露「是否需要构建 npm」的开关。
改动很小，但需要先用一个真实带 npm 依赖的原生项目验证，否则容易改出「本来能传的传不了」。

## 六、建议的执行顺序

| 顺序 | 组 | 为什么放这个位置 |
|---|---|---|
| 1 | **A 认证** | 必须全绿，否则后面无法进行 |
| 2 | **B / C / D 基础资源** | 准备凭证与机器人（D 组无 webhook 可跳过） |
| 3 | **E 项目管理** | 先把项目建对——尤其是**产物目录**，这里配错会让后面所有构建「成功但包是空的」 |
| 4 | **黄金路径 + G1 + G18** | 一次端到端；**G18（包体积合理性）是「构建真的通了」的唯一硬证据** |
| 5 | **G 组其余**（G2~G14） | 核心价值所在，G13 验证 robot 分配 |
| 6 | **F 成员与权限** | F-1 已修复，预期应当全绿；若有失败，是新的回归 |
| 7 | **H / I / J / K 周边** | 收尾 |

**门槛规则**：第 4 步必须同时满足「状态 success」+「包体积在百 KB~MB 级」+「二维码可预览」，
才算构建链路打通。只满足第一条的话，后面所有构建用例的结论都不可信。

每轮执行前建议重置数据：`prisma migrate reset --force` 后重启服务（会重建 admin 账号与机器人池）。

> 重置后 `var/logs`、`var/cache`、`public/storage` 里的旧文件仍会保留，如需干净环境手动清。
